# Пространственный стык крупной и мелкой сеток

Реализован второй этап сгущения: **два одновременно работающих уровня
с прямоугольной мелкой областью и двумя мелкими подшагами на один крупный**.
Снаружи мелкой области находятся настоящие крупные ячейки. Их состояние
передаётся на мелкий уровень, а мелкий уровень возвращает состояние
и фактические потоки через стык.

Это исследовательский расчёт **жидкости без тела в периодической области**.
Стенки профиля, открытые внешние границы, нагрузки и многоуровневое
продолжение относятся к следующему этапу. В рабочее окно расчёта профиля
эта возможность пока не подключена; равномерная сетка там сохраняется.

Код:
[interface.py](../src/aerokinetic/interface.py),
[interface_checks.py](../src/aerokinetic/interface_checks.py),
[interface_visualization.py](../src/aerokinetic/interface_visualization.py).
Операторы разового переноса из [первого этапа](REFINEMENT_RU.md)
используются для заполнения донорских ячеек и обратного усреднения.

## Принадлежность ячеек

`FineBox(lower, upper)` задаёт полуоткрытые целочисленные границы
в индексах крупной сетки. Мелкая область начинается и заканчивается
на гранях крупных ячеек. Внутри каждой крупной ячейки — восемь мелких.

Крупные ячейки под мелкой областью — **виртуальные**: они дают прогноз
для донорских значений и не включаются в массу/импульс составного решения.
Этот объём принадлежит мелким ячейкам. Маска принадлежности сохранена
и используется при интегрировании и выводе полей.

Область может целиком охватывать периодическую ось, например размах z.
В этом случае донорские слои на концах этой оси берутся из собственного
периодического мелкого решения; стыка с крупной сеткой на этих концах нет.
Для остальных осей мелкая область должна лежать строго внутри крупной.
Пересекающие периодическую границу блоки, несколько блоков и более двух
уровней пока не поддерживаются.

## Один крупный шаг

1. Сохраняются крупные PDF до столкновения при `t`. Выполняются крупное
   столкновение и streaming, получается прогноз при `t+dt_c`.
2. Из крупных состояний при `t` и `t+dt_c` заполняется мелкая донорская
   оболочка при `t`; настоящий внутренний мелкий объём сохраняется.
3. Выполняются первое мелкое столкновение и streaming. Через все
   грани мелкой области регистрируются фактические потоки.
4. Донорская оболочка обновляется интерполяцией при `t+dt_c/2`;
   выполняются второе мелкое столкновение и streaming с учётом потоков.
5. Разность мелких и крупных потоков локально исправляет плотность
   и импульс только крупных ячеек, прилегающих к граням стыка.
6. Синхронизированное мелкое состояние усредняется в виртуальные крупные
   ячейки. Целые счётчики времени увеличиваются на 1 и 2 соответственно.

`dx_f=dx_c/2`, `dt_f=dt_c/2`, а релаксации на уровнях согласованы по
физическим сдвиговой и объёмной вязкостям, как в первом этапе.
Оба слоя используют cumulant D3Q27 lbmpy 1.4, float64, без силы и SGS.
PDF имеют стадию **до столкновения**. Массивы из прежнего производственного
`Solver`, хранящего другую стадию, нельзя передавать сюда напрямую.

## Почему нужен поток через грани, включая углы

Простое присвоение диагонального перелёта одной крупной ячейке нарушает
соответствие потоков возле углов блока. Здесь streaming раскладывается
в последовательные сдвиги по координатам. Для одного направления:

```text
Ex Ey Ez - I = (Ex-I) + Ex(Ey-I) + Ex Ey(Ez-I)
```

Это точное дискретное тождество. Усреднение всех шести порядков координат
сохраняет его и убирает предпочтение одного порядка обхода осей.
Каждая часть записывается как разность потоков через две грани ячейки.
Масса и три компоненты импульса берутся из **настоящих PDF после
столкновения**, которые затем участвуют в streaming.

Если `Phi` — этот поток в решёточных единицах, интегральный перенос
за один шаг равен `V_cell*Phi`. Мелкий поток суммируется по четырём
дочерним граням и двум подшагам. Поправка соседней крупной ячейки:

```text
delta(rho,j) = sign * (sum_fine[V_f Phi_f] - V_c Phi_c) / V_c
```

Знак зависит от стороны блока. Единица физической скорости `dx/dt`
одинакова на обоих уровнях; при выводе физического импульса она учитывается.
Поправка вносится разностью равновесий при новых и старых `rho/j`,
сохраняя прежнюю неравновесную часть PDF. Проверяются положительность
плотности и физических PDF. Общая подгонка средней плотности, clipping
и скрытая смена вязкости не применяются.

Само точное тождество потоков не доказывает точность интерполяции,
устойчивость при любом Re или пригодность для турбулентной стенки.
Поэтому выполнены отдельные задачи на перенос волны, вихря и звука.

## Проверки

Допуски зафиксированы до расчётов в
[PLAN.json](verification_interface/PLAN.json);
для вывода полей — в [EXPORT_PLAN.json](verification_interface/EXPORT_PLAN.json).
Итоги и сырые данные — в [отчёте второго этапа](verification_interface/REPORT_RU.md).

- Точный баланс streaming сравнивается с прямым независимым сдвигом PDF.
- Однородные покой и поток проходят через грани, рёбра и углы без
  искусственного изменения плотности/импульса.
- Проверяются два подшага, настоящие периодические мелкие доноры и
  локальность поправки. При отключении поправки баланс должен нарушаться.
- Наклонная сдвиговая волна и 3D вихрь проходят конечную мелкую область;
  используется три разрешения при одинаковых физических параметрах.
- Для вихря проверены вход через грань, ребро и угол. Аналитический
  эталон — линейный перенос и диффузия гауссового векторного потенциала
  при малой амплитуде; нелинейность/сжимаемость не объявляются строго нулевыми.
- Акустический импульс проходит область в обоих направлениях. Избыток
  обратной характеристики сравнивается с собственным равномерным расчётом.
  Это верификация алгоритма, а не сравнение с чужой CFD-программой.

Пространственные ошибки этой серии относятся к названным гладким задачам.
Ни они, ни сохранение массы не подтверждают Cl/Cd/Cm профиля. Продувки
остаются основанием будущей аэродинамической валидации.

## Срезы и анимация

Контрольный вихрь при N=32 сохраняет 21 срез при `z=8`, от t=0 до t=80.
На одну и ту же плоскость интерполируются плотность и импульс обеих сеток.
По x/y изображаются фактические грани ячеек без сглаживания.
Цвет показывает `|u-U0|/A` с одной шкалой для всей анимации.
Это скорость возмущения контрольного вихря, а не поле аэродинамического
профиля и не скорость в метрах в секунду.

Сохраняются NPZ с координатами/масками/временем, PNG и GIF через Pillow.
Ни браузер, ни ffmpeg, ни интернет для этого не нужны. Это пока отдельный
научный экспорт; он не заменяет производственный формат полей приложения.

## Воспроизведение

В окружении с установленной проверочной сборкой и локальным компилятором:

```text
python -m aerokinetic.cli verify-interface --output interface_check_01
```

Для одних численных проверок доступен `--no-plot`. Для проверки
установленного wheel в чистой среде с пустыми кешами:

```text
python tools/check_refinement_offline.py --interface --output interface_offline_01
```

Используются прежние закреплённые зависимости. Проверяется путь импорта
из wheel, блокируются Python socket-соединения и DNS. Это контроль
обращений Python; отключение сети на уровне ОС не утверждается.
Здесь проверен Linux CPU; Windows/MSVC и GPU требуют своих запусков.

До выделения массивов проверяется оценка памяти и заданный лимит.
Оценка включает временные поля и запас на JIT; она отличается от
измеренного пика процесса. После ошибки посреди шага объект требует
повторного `initialize`: продолжать частично обновлённые уровни нельзя.

Следующий этап — стенки профиля, открытые границы, силы/момент,
история и контрольные состояния обоих уровней, затем исследования
сходимости и сравнение с продувками. См. [ROADMAP_RU.md](ROADMAP_RU.md).
